# 테스트용 축소본 명세 (IBM HI-Small → ibm_small) — 초안 v0.1

읽는 사람: 준혁(적재·룰 테스트에 쓴다), 준영(정답지 숫자를 확인한다), 진희(만든다).
한 줄: **508만 건(5,078,345)은 시연용, 통합 테스트와 CI는 약 1만 건짜리 고정 파일로 돈다.** 그 파일을 어떻게 만들고 어디에 두고 어떻게 쓰는지.

## 1. 데이터 세 단계

| 단계 | 크기 | 위치 | 용도 | 누가 |
|---|---|---|---|---|
| ① 룰별 손수 CSV | 룰당 10~50행 | `src/test/resources/rules/R01_fan_in.csv` … | 룰 단위 테스트. "이 입력이면 경보 2건"이 눈에 보임 | 준혁 — 룰 만들 때 같이 (TDD) |
| ② 축소본 `ibm_small` | 약 1만 행, 1~2 MB | `src/test/resources/fixtures/ibm_small/` (리포 커밋) | 통합 테스트·CI. 적재 → 룰 스캔 → 점수 → 케이스 실제 흐름 | 진희 — W1 뼈대에 포함 |
| ③ IBM 전체 | 약 508만 행 | 각자 PC, 리포 밖 (`.gitignore`) | 시연, 적재·배치 시간 측정 | 준혁 — W2 |

## 2. 축소본 만드는 법 — 날짜가 아니라 "패턴 단위"로

하루치를 잘라도 70만 건이라 CI용으론 크고, 며칠에 걸친 패턴(순환·분산 송금)이 중간에 끊겨 룰이 안 걸린다. 그래서:

1. `HI-Small_Patterns.txt`(IBM이 주는 자금세탁 패턴 파일)에서 **유형 8개 × 2개 = 16개 패턴**을 고른다 (seed 고정, 거래 80건 넘는 큰 패턴은 피함).
2. 그 패턴에 등장하는 계좌(은행코드+계좌)를 모은다 — 100~200개.
3. 그 계좌가 보내거나 받은 거래를 **전체 기간(9/1~9/18)에서 전부** 가져온다 → 패턴이 안 끊기고 라벨 거래가 반드시 들어간다.
4. 정상 거래(라벨 0, 패턴 계좌와 무관)를 **무작위 약 7,000건** 섞는다 — 오탐이 나올 "배경"이 있어야 룰 테스트가 의미 있다.
5. 다른 패턴(안 고른 것)의 라벨 거래가 섞여 들어오면 뺀다 → `labeled` = 고른 16개 패턴의 거래 수와 정확히 같다.
6. **원본과 같은 헤더·컬럼·타임스탬프 형식**으로 저장한다. 적재 배치 `LoadIbmDataset`은 경로만 바꿔 그대로 읽는다. 타임스탬프는 2022년 9월 원본 그대로 → `rule-scan?date=2022-09-02` 식으로 그대로 쓴다.

도구: `tools/make_fixture.py` (아래 3절). 같은 seed면 항상 같은 파일이 나온다. `_meta`에 원본 파일 해시를 남겨 "어느 원본에서 뽑았나"를 추적한다.

```
python tools/make_fixture.py --trans data/HI-Small_Trans.csv --patterns data/HI-Small_Patterns.txt \
       --out src/test/resources/fixtures/ibm_small --per-type 2 --background 7000 --seed 20261027
python tools/draft_alerts.py --fixture src/test/resources/fixtures/ibm_small
```

## 3. 산출물 세 파일

```
src/test/resources/fixtures/ibm_small/
  HI-Small_Trans.csv       축소본 거래 (원본과 같은 형식)
  HI-Small_Patterns.txt    고른 16개 패턴만 (원본과 같은 BEGIN/END 형식) → customer_attributes 생성에 사용
  expected.json            정답지
```

`expected.json` 구조:

| 키 | 뜻 | 누가 채우나 | 어느 테스트의 기준인가 |
|---|---|---|---|
| `rows`, `labeled`, `accounts`, `per_day`, `date_range`, `amount_paid_sum_by_currency` | 적재 결과가 맞는지 | 스크립트가 자동 | 준혁 — 적재 검증 쿼리 5개 (행 수·라벨 수·날짜 범위·계좌 수·금액 합) |
| `patterns` | 유형별 패턴 수 | 스크립트가 자동 | customer_attributes 생성 검증 |
| `alerts.by_date[날짜][R0x]` | 날짜별·룰별 경보 수 | **초안은 `draft_alerts.py`(v0.1 정의), 확정은 준영 님(10/27 룰 정의 확정 후)** | 준혁 — 룰 스캔 테스트 ("9/2 스캔 = pandas 값") |
| `alerts.params` | 룰 임계값 | 규약 2절 그대로 | 셋이 같은 값을 봐야 함 |
| `_meta` | seed, 원본 해시, 만든 날 | 스크립트가 자동 | 재현성 |

경보 1건의 정의: **(룰, 날짜, 대상 계좌)** 한 조합 = 1건. 근거 거래 ID는 백엔드가 붙인다. pandas와 SQL이 다른 숫자를 내면 코드보다 **정의 문장**을 먼저 의심한다 — 그게 이 파일의 목적이다.

## 4. 테스트에서 쓰는 법 (준혁)

- Testcontainers PostgreSQL은 **싱글턴 하나**. 클래스마다 띄우지 않는다. 한 번 뜨고 Flyway 돌리고 축소본을 한 번 적재한 뒤 모든 통합 테스트가 공유한다. 1만 행이면 적재 2~3초, CI 전체 1분 안쪽이 목표.
- 적재 테스트: `LoadIbmDataset(fixture 경로)` → `batch_runs` SUCCEEDED → 검증 쿼리 5개 결과를 `expected.json`과 비교.
- 룰 테스트 두 층: ① `rules/R01_fan_in.csv` 10~50행으로 `FanInRule.evaluate` 단위 테스트(DB 없이) → ② 축소본에 `RunRuleScan(date)` 돌려 `alerts.by_date` 와 비교.
- 케이스·STR 테스트는 축소본이 필요 없다. 빈 DB + 테스트 데이터 몇 줄.
- 축소본은 **절대 손으로 고치지 않는다.** 바꿀 일이 있으면 스크립트 파라미터를 바꾸고 다시 뽑고, `_meta`가 바뀐 걸 PR에 적는다.

## 6. 초안을 돌려 보면 바로 보이는 것 (예)

합성 샘플로 돌린 결과, v0.1 정의 그대로면 R05(경유 송금: 받은 돈 80%를 24시간 안에 내보냄)가 배경 거래에서 42건 걸렸다 — 임계값이 너무 느슨하거나 "최소 금액" 조건이 빠진 것. 반대로 R04(순환)는 A→B→A 2단만 봐서 A→B→C→A 3단 순환을 못 잡았다. **이런 걸 10/27 전에 발견하는 게 이 초안의 쓸모다.** 실제 IBM 데이터로 돌리면 더 나온다.

## 7. 확인할 것 하나

IBM 데이터를 잘라 공개 리포에 커밋해도 되는지 **라이선스 확인**. 안 되면 축소본은 커밋하지 않고 CI에서 원본(캐시)으로 스크립트를 돌려 만든다 — 같은 seed라 결과는 같다.
