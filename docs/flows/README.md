# docs/flows — 폴더가 만나는 지점의 그림

각자 폴더 안쪽 흐름은 담당자 문서에 있다(준혁 개발 계획서, 지윤 CASES 안내, 채영 STR 문서). 여기는 **폴더와 폴더, 백엔드와 AI, 사람과 시스템이 만나는 지점**만 그린다. Mermaid라 GitHub·IntelliJ에서 바로 보인다. 코드가 바뀌면 그림도 같은 PR에서 고친다.

| 파일 | 무엇 | 누가 먼저 보나 |
|---|---|---|
| [01_batch_chain.md](01_batch_chain.md) | 적재 → 룰 스캔 → ML 특징·점수·근거 → 케이스 생성. `BatchRun`은 shared | 준혁, 준영, 지윤 |
| [02_investigation.md](02_investigation.md) | 로그인 → 목록 → 상세(+요약) → 배정 → 에스컬레이션. 현재 초안은 프론트가 따로 부름 | 지윤, 프론트 |
| [03_str.md](03_str.md) | 초안 요청(트랜잭션 밖) → 저장 → 수정 → 검증 → 승인(한 트랜잭션) | 채영 |
| [04_failure_paths.md](04_failure_paths.md) | 점수의 통신·경보별 품질 실패와 재시도(시나리오 9), 초안 요청 실패(시나리오 7) | 준혁, 준영, 채영 |
| [05_login_auth.md](05_login_auth.md) | 로그인·세션·CSRF, 권한이 막히는 네 지점, 계정 발급 | 프론트, user 담당 |
| [06_alert_lifecycle.md](06_alert_lifecycle.md) | 경보 하나의 일생. 유효 점수와 계산 실패 분기, 화면↔상태↔버튼 표 | 준영, 프론트, 발표 |

그림에 나오는 이름은 백엔드 설계 레퍼런스의 유스케이스·테이블 이름 그대로다. 그림과 설계 문서가 다르면 설계 문서가 맞고, 그림을 고친다.

## ML 연동 보완 범위 (2026-10-22)

준영 담당의 점수 파이프라인과 입출력 처리 기준을 ①·④·⑥에 반영했다. 특징 계산·점수·설명·근거·AI 예측 기록을 보여주며 구현 완료를 뜻하지 않는다. ② 조사, ③ STR, ⑤ 로그인·권한과 ④의 STR 실패 그림은 변경하지 않았다.

- 입력: 확정된 경보 계약의 ID·대상 거래·기준 시점. 학습과 서비스에서 같은 특징 함수를 사용하고, 서비스에 학습용 LI·SAML 거래 ID를 섞지 않는다.
- 결과: HTTP 상태와 별도로 경보별 점수·품질·버전·근거를 검증한다. 계산 실패는 0점·LOW가 아니며 `FAILED`로 구분한다.
- 재요청: 같은 경보·입력·모델/특징 버전은 기존 `prediction_id`와 저장 결과를 재사용한다. HTTP 요청 시도 로그는 별도다. 배치와 재시도 동안 모델/특징 버전을 고정한다.

## ML 연동에서 공통 확인이 필요한 항목

아래는 준혁·공통 담당과 확인할 사항이며, 이 문서 수정으로 DB 제약·배치 enum·공통 정책이 확정된 것은 아니다.

| 항목 | 확인할 내용 |
|---|---|
| 동시 실행과 재실행 | 동시 실행 차단과 실패 대상 보충 실행을 구분. 점수 재시도 뒤 추가 HIGH 경보의 케이스 생성이 막히지 않아야 함 |
| 배치 유형·요약 상태·건수 | 원문의 `SCORE_RETRY`, `PARTIAL`과 기존 가이드가 불일치. 재시도 유형, 요약 상태, 성공·실패 건수 저장 기준 확정 |
| 자동 재시도 | `AiClient`의 횟수·대상 오류·단일 요청/전체 실행 시간 한도 확정. ML에서 별도의 중첩 재시도는 만들지 않음 |
| 점수 저장 중복 방지 | AI의 같은 `prediction_id` 재사용과 백엔드 DB 제약을 연결. 다른 모델 버전의 점수 이력을 보존할 수 있어야 함 |
| 응답 계약 | 설명·품질·특징 버전 필드명과 경보별 실패 표현은 확정 규약 및 공통 Pydantic 모델 한 벌에 맞춤. 그림의 축약 표기는 새 JSON 계약이 아님 |
