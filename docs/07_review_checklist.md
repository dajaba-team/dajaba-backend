# 07. PR 리뷰 체크리스트

> v0.1 · 2026-10-29 · 초안(팀 확인 중) · 정리 진희

리뷰할 때 보는 항목과 근거 위치예요. **확정된 규칙만 리뷰 기준**으로 써요. 담당자 초안과 다르게 짠 건 지적이 아니라 질문으로("초안과 다른데 의도한 건가요?"), 〔제안〕 항목은 `[제안]` 코멘트로만 남겨요.

## 0. 위험도 — 어디부터 꼼꼼히 볼지

| 위험도 | 이런 PR | 보는 깊이 |
|---|---|---|
| **상** | `shared/`·`SecurityConfig`·권한 검사, Flyway(스키마), 상태 전이(`CaseStatus`·`Case`·`StrDraft`), 승인·반려·`ApprovalGate`, 협력 트랜잭션, AI 호출 흐름 | 전부. 테스트를 직접 돌려 보기 |
| **중** | 새 API, 배치, 새 유스케이스, 집계 쿼리 | 아래 체크리스트 전부 |
| **하** | 조회 API, 문서, 테스트만, 이름 정리 | 1·2·7·8절 위주 |

리뷰 대기열은 **다른 사람을 막는 PR → 오래된 PR → 작은 PR** 순서로 봐요.

## 1. PR 자체 [PR 템플릿, 컨벤션]

- [ ] 대상이 `develop`, 브랜치가 `{type}/SCRUM-xx`
- [ ] 제목·본문에 Jira 키와 링크
- [ ] "확인 방법"에 실행 OS와 `./gradlew test` 결과(`ArchitectureTest` pass, `ApplicationContextTest` pass/skip)
- [ ] CI 초록불
- [ ] 한 가지 일, ≤400줄(생성 파일 제외)
- [ ] 커밋 메시지 `Gitmoji type: 내용`
- [ ] `TODO`에 안건 번호 (`// TODO(Open-11):`)
- [ ] 새 라이브러리면 3줄 사유
- [ ] "참조한 문서"에 따른 절 번호가 있음

## 2. 구조·계층 [`02_structure.md`]

- [ ] 클래스가 맞는 계층에 있음 (if 문에 업무 용어 → domain, 여러 리포지토리 → application, 바깥 → infrastructure, HTTP → api)
- [ ] 다른 기능은 **application 유스케이스로만** 부름. 다른 기능 엔티티의 상태를 바꾸지 않음
- [ ] 다른 애그리거트는 **ID로** 참조(`caseId`), 객체 참조 아님
- [ ] **컨트롤러가 리포지토리를 직접 부르지 않음** (ArchitectureTest가 못 잡음)
- [ ] **엔티티를 응답으로 그대로 내보내지 않음** (응답 record) (못 잡음)
- [ ] `shared/`를 고쳤다면 진희 확인

## 3. 엔티티·도메인 [README 규칙 2, 가이드 §4, 레퍼런스 §5]

- [ ] `setStatus()`·public setter 없음. 상태는 전이 메서드로만 (못 잡음)
- [ ] 업무 규칙(상태 검사)이 엔티티 안에. 유스케이스에 `if (x.getStatus() == …)` 없음
- [ ] 전이 가능 여부는 enum 한 곳, 전이마다 이력 한 행이 엔티티 안에서 추가됨
- [ ] 그림(가이드 §4·`06_features/cases.md` 전이 표)에 없는 화살표를 추가하지 않음
- [ ] 이력 테이블 엔티티에 수정·삭제 메서드 없음
- [ ] `cases`·`str_drafts` 변경엔 `@Version`
- [ ] 반려 뒤 이동 검사는 **cases의 반려 코드 값**으로 [안건 24]

## 4. 트랜잭션·AI 호출 [가이드 §5, 레퍼런스 §8.4]

- [ ] `@Transactional`은 application에만, 읽기는 `readOnly = true` (못 잡음)
- [ ] **AI 호출이 트랜잭션 밖** ("DB → HTTP → DB") (못 잡음)
- [ ] AI 응답 저장 때 상태·담당자·version을 다시 확인 → 그사이 종료됐으면 저장 거절
- [ ] AI 실패 때 케이스 상태를 되돌리지 않음
- [ ] AI 응답 원문은 `payload jsonb`, 필터·정렬 값만 컬럼
- [ ] 함께 성공·실패해야 하는 것이 같은 트랜잭션 (케이스 생성 + `MarkCaseOpened`, 승인 + LOCKED + APPROVED, 초안 있는 종료 + SUPERSEDED). 협력 트랜잭션에 `REQUIRES_NEW`를 쓰지 않음
- [ ] 배치 상태 기록은 본 작업과 다른 트랜잭션(실패 기록이 남게)
- [ ] `GENERATION_IN_PROGRESS`·4xx·예산 초과를 자동 재시도하지 않음 [안건 21·23]
- [ ] 점수 `FAILED`를 0점·LOW로 바꾸거나 지우지 않음 [안건 4]

## 5. DB·Flyway [`05_flyway.md`]

- [ ] 새 파일 **1개**, 번호는 팀 채팅에 예약된 것
- [ ] 이미 있는 `V00x` 파일을 고치지 않음
- [ ] 상태 값은 `varchar` + `CHECK`
- [ ] 사람이 고치는 테이블엔 감사 4(`BaseEntity`), 추가만 테이블엔 `created_at`(+`created_by`)만
- [ ] 이력 테이블에 `revoke update, delete … from app_backend`
- [ ] 필터·정렬에 쓰는 값은 컬럼 + 인덱스
- [ ] `ai` 스키마 FK 없음, 원천 테이블에 컬럼 추가·UPDATE 없음

## 6. API [레퍼런스 §8.2·§12, `03_shared.md`]

- [ ] 경로 `/api/v1/{리소스}/{사람이 보는 번호}/{동사}`, 상태 변경은 POST
- [ ] 요청 record에 `@Valid` + 길이 제한 (`comment` 2,000 · 메모 10,000 · 섹션 5,000)
- [ ] 요청 body로 사용자 ID를 받지 않음 → `CurrentUser`
- [ ] 변경 요청에 `version`
- [ ] 에러는 `{error: {code, message, details}}`, 409 이름은 `INVALID_CASE_TRANSITION`·`CONCURRENT_UPDATE`
- [ ] 목록은 페이지 규칙(`size` ≤ 100, 정렬 화이트리스트)
- [ ] 빈 목록 `[]`, 없는 값 `null`
- [ ] `@JsonProperty` 없음, 금액 `BigDecimal`, 시각 타입 섞지 않음
- [ ] 목록은 `PageResponse.from(page)` → `{items, page, size, total}` [SCRUM-39]
- [ ] 〔제안〕 새 에러 코드가 `03_shared.md` §2 표에 있음
- [ ] 조회 유스케이스에서 열람 기록(`access_logs`)이 필요한 곳엔 남김 (케이스 상세, 초안 상세, 근거 원본, 경보 상세)

## 7. 보안·로그 [레퍼런스 §10, `01_code_rules.md` §6·§7]

- [ ] 계좌번호는 뒤 4자리만, `is_laundering`·패턴 정답이 응답·요청·로그 어디에도 없음
- [ ] 로그에 금액·계좌번호·고객명·본문·비밀번호·키 없음
- [ ] SQL 파라미터 바인딩, 정렬 컬럼 화이트리스트
- [ ] 비밀값·URL·매직 넘버 하드코딩 없음 (`.env` · `AmlProperties`)
- [ ] 권한: URL 단위(`SecurityConfig`)와 객체 단위(담당자 확인) 둘 다. 테스트는 `@WithMockUser`, `SecurityConfig`를 고쳐서 통과시키지 않음

## 8. 테스트 [레퍼런스 §6, PR 템플릿]

- [ ] 정상 1 + 경계 1 + 실패 1
- [ ] 상태 전이·승인 게이트·룰 판정은 **테스트가 먼저**(허용 전이 하나 = 테스트 하나, 금지 전이·끝 상태도)
- [ ] 유스케이스 통합 테스트는 이력 행이 실제로 들어갔는지 DB에서 확인
- [ ] H2 없음, 리포지토리 Mockito 모킹 단위 테스트 대신 Testcontainers 통합 테스트

## 9. 문서 [flows README, 컨벤션]

- [ ] 폴더 사이 흐름이 바뀌었으면 같은 PR에서 `docs/flows` 그림도 고침
- [ ] 공통 인터페이스(규약·공통 응답)를 바꿨으면 담당자와 사전 협의, 노션 갱신
- [ ] README "지금 들어 있는 것" 표에 영향이 있으면 갱신
- [ ] 〔제안〕 `shared/`·보안 설정 변경이면 #개발 공지 네 줄 (`03_shared.md` 맨 위)

## 10. 기능별로 더 보는 것

**source** — 원천은 COPY로, 적재 트랜잭션이 원천 4개 전부를 감쌈, 검증 쿼리, 빈 DB에서만 적재, `transaction_id`·`source_files` 규칙(안건 1), 은행 ID 형식(〔확인 필요〕)

**detection** — 집계는 SQL·판정은 Java, 기준값 없으면 예외(기본값 금지), 룰 공통 네 가지(통화별·달력일·`reference_ts`=창 끝·자기계좌 제외), 룰 스캔은 한 트랜잭션, 점수는 500개 묶음마다 커밋, `score_band`를 detection에서 정하지 않음(CasePolicy), `MarkCaseOpened`는 부르는 쪽 트랜잭션에 참여, R04·R05 `paths`

**cases** — 전이 표 그대로, 반려 코드 분기, 케이스 생성은 HIGH만·경보별 한 트랜잭션·보충 실행 허용, CasePolicy에 임의 기본 경계값 없음, cases → str 의존 없음

**str** — 숫자·근거는 수정 불가, 검증은 **지금 본문 해시**로 찾기("최신 검증" 아님), `ApprovalGate` 여섯 조건, `draft_id` 선발급, 생성·검증 별도, 반려 코드·사유 필수(400), 승인 대기 중 수정 불가, 해시 테스트 벡터

**user·shared** — 로그인 실패 메시지 하나, 세션 30분·동시 1개, CSRF, 비밀번호 BCrypt 12·평문 없음, 로그인 실패 응답이 사유마다 같은지, 역할 변경 시 세션 끊기

## 11. 리뷰 코멘트 쓰는 법 [컨벤션]

근거와 개선 방향을 함께 쓰는 **제안형**으로 써요.

```
[반드시] (파일:줄) 무엇이 왜 문제인지 — 근거: 레퍼런스 §8.4 / README 규칙 2
         이렇게 바꾸면 돼요: …
[제안]   …
[질문]   초안(CASES 명세 v0.5)과 다르게 짰는데 의도한 건가요?
[좋아요] …
```

- `[반드시]`는 **확정 규칙 위반**에만 써요. 초안과 다른 건 `[질문]`.
- 요청자는 코멘트마다 반영 여부나 의견을 남겨요.
- 서로 다른 사람에게 같은 지적이 두 번 나오면 `02_structure.md` §7 자동 검사 후보로 올려요.
