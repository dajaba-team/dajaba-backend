## 1. 여섯 룰 공통 규칙

1. **룰 ID** — 위 표의 `rule_id` 문자열을 코드·`rules.rule_id`·학습 데이터에 그대로 써요. **시간은 ID에 넣지 않고** 창 길이는 `params.window_hours`에 둬요.
2. **경보 1건** — (룰, 대상 계좌, 창) 한 조합. 대상 계좌는 룰마다 적어요.
3. **자기 계좌 거래 제외** — `is_self_transfer = true`는 모든 룰에서 세지도, 근거에 넣지도 않아요. 그래서 경보·경로·III부에 들어가지 않아요(0건).
4. **금액은 방향대로** — 입금은 `amount_received`·`currency_received`, 출금은 `amount_paid`·`currency_paid`(B7 ③, 11/2). **다른 통화끼리 더하지 않아요.** 비교에 환산을 쓰는 건 R03 하나뿐이고(2절 R03), `rule_facts`에 적는 금액은 어느 룰이든 원래 통화 그대로예요.
5. **통화 표기** — `rule_facts`의 통화는 원문 그대로(`US Dollar`). 코드(`USD`) 변환은 STR facts에서 AI가 해요.
6. **여러 통화** — 같은 계좌·룰·창이면 통화와 상관없이 **경보 1건**. 금액은 통화별 배열(`amounts_by_currency` 등). 단일 통화도 배열 한 항목(ML 규약 §2.3).
7. **근거 거래** — `transaction_ids` = 조건을 성립시킨 거래 전부(거래 id 순, 중복 없음). 통화별·방향별·경로별 거래 id의 합집합과 같아요. 상한 없음.
8. **시각** — 원천 시각은 **분 단위**(초 없음). 저장값은 시간대 없는 원본 시각. ML 피처는 `ts < reference_ts`.
9. **같은 분은 앞뒤를 모른다** — 분 단위라 같은 분 거래의 선후는 알 수 없어요. "A 다음에 B"가 조건인 룰(R03·R04·R05)은 **B가 A보다 늦은 분**일 때만 인정해요.
10. **`batch_date`** — 스캔한 날짜 = 평가 시점 E의 날짜(창 끝이 다음 날 00:00이어도).
11. **기준값이 없으면 실패** — `rules.params`에 필요한 키가 없거나 잘못되면 409 `INVALID_RULE_PARAMS`, 배치 FAILED. 코드에 기본값을 두지 않아요. `window_hours`도 마찬가지예요.

### 1.1 슬라이딩 창 (B7 — 여섯 룰 모두)

H = `params.window_hours`(v2는 모두 96).

- 창 = **`[E+1분 − H, E+1분)`** — 뜻은 **`(E − H, E]`**: 지금 분 E는 넣고, 정확히 H 전 그 분은 빼요. 저장값은 규약의 `[시작, 끝)` 표기라 1분 민 값이에요: `window_start = E+1분−H`, `window_end = reference_ts = E+1분`.
- **거짓→참일 때만 경보.** 1분 전 창 `[E−H, E)`의 조건과 비교해요. 참이 이어지는 동안은 경보를 더 만들지 않아요.
- 거래가 없는 동안 옛 거래가 창 밖으로 빠져 거짓이 되고, 다음 거래 분에 다시 참이 되면 **새 경보**.
- 날짜 경계: 전날 밤부터 참이 이어지면 다음 날에는 경보가 없어요. 전날을 스캔하지 않았어도 결과는 같아요.
- 경로·중계 룰(R03·R04·R05)은 경로의 **모든 거래**가 창 안에 있어야 해요.

예 (R02, N = 2, H = 96): A로 11-07 06:00 S1, 07:00 S2, 08:00 S3 입금 → 06:00은 1명이라 없음, **07:00에 2명(1분 전 창은 1명) → 경보**, 08:00은 참 유지라 없음. 경보 창 `[11-03 07:01, 11-07 07:01)`, 근거 S1·S2 거래.

### 1.2 평가 시점 — 관련 거래가 있는 분에서만

시간이 흐르는 것만으로 모든 분을 평가하지 않아요. **새 관련 거래가 생긴 분 E에서만** 지금 창과 1분 전 창을 비교해요.

| 룰 | E |
|---|---|
| R01 | 대상 계좌가 **송금**한 분 |
| R02 | 대상 계좌에 **입금**이 있었던 분 |
| R06 | 대상 계좌에 **입금이나 출금**이 있었던 분 |
| R03 | 중계를 완성하는 **출금**이 있었던 분 |
| R04 | 고리를 닫는(A로 **돌아오는**) 거래의 분 |
| R05 | 경로를 완성하는 T **입금**의 분 |

- **만료만으로 생긴 거짓→참은 경보가 아니에요.** 예: R06 입금 상대가 101명 → 100명으로 줄어 조건이 참이 됐어도, 그 변화가 옛 거래가 창에서 빠져서 생긴 거면 경보를 만들지 않아요. 다음 관련 거래가 있는 분에 참이면 그때 경보예요.
- 오프라인 분석(9/1~9/10 수치)도 같은 방식이라 수치가 달라지지 않아요.

### R03_FX_RELAY — 환전 중계 〔확정 — v1 `R03_PASS_THROUGH`를 대체〕

번호만 이어 쓰고 뜻이 달라서 ID를 바꿨어요. 옛 R03(같은 통화 누적 유출)은 v1 평가에서 무작위 수준(lift 1.20)이라 뺐어요. HI-Small의 STACK·RANDOM은 받은 돈을 **다른 통화로 거의 같은 금액** 넘기는 모양이 많아서, 그걸 직접 잡아요.

| 항목 | 내용 |
|---|---|
| 중계 쌍 | 계좌 M이 받은 거래 a(받은 통화 `currency_received`)와, a보다 **늦은 분**에 M이 보낸 거래 b(보낸 통화 `currency_paid`). 둘 다 창 안 |
| 조건 | ① `require_currency_change`면 b의 보낸 통화 ≠ a의 받은 통화 ② 비율 = (b `amount_paid` ÷ `usd_rates[b 통화]`) ÷ (a `amount_received` ÷ `usd_rates[a 통화]`)이 `[1 − amount_tolerance, 1 + amount_tolerance]` 안(**양 끝 포함**, v2는 0.9~1.1) |
| 대상 계좌 | M(중계 계좌) |
| 창 · E | 1.1 · 1.2 — E = 중계 쌍을 완성하는 **출금**의 분. 조건 = "창 안에 중계 쌍이 1개 이상", 거짓→참 |
| 출금 상한 | 없음 — 받은 거래마다 창 안의 출금을 **전부** 봐요(상한을 둬도 결과가 같은 걸 확인, 11/9) |
| `params` | `{"window_hours": 96, "amount_tolerance": 0.1, "require_currency_change": true, "usd_rates": {…}}` — 아래 표 |
| `rule_facts` | 〔제안〕 `{paths:[[a, b], …], relays:[{in_currency, in_amount, out_currency, out_amount, ratio}]}` — `paths`는 중계 쌍마다 [받은 거래, 보낸 거래](2.1 모양), `relays`는 같은 순서. 구현 PR(SCRUM-193)에서 학습용 쪽과 확정 |
| 근거 거래 | 창 안 모든 중계 쌍의 거래(합집합) |
| 한계 | 환율이 실시간이 아니라 HI-Small 고정값이에요. 결제 수단(ACH)은 조건에 넣지 않았어요 — 생성기가 세탁 거래에 ACH를 일괄로 써서 데이터에 과적합돼요 |

### R04_CYCLE — 순환 거래 〔확정〕

| 항목 | 내용 |
|---|---|
| 고리 | 거래 t1(A→B) … tk(→A), **2 ≤ k ≤ `max_hops`**. 앞 거래의 수신 계좌 = 다음 거래의 송신 계좌, 시각은 **분 단위로 엄격히 증가**(같은 분 불인정), 중간 계좌는 서로 다르고 A가 아님 |
| 대상 계좌 | A = 고리의 첫 거래(가장 이른 거래)의 송신 계좌. 그래서 같은 고리가 B·C 쪽에서 또 잡히지 않아요 |
| 창 · E | 1.1 · 1.2 — E = A로 **돌아오는 거래**(고리의 마지막 거래)의 분. 고리의 모든 거래가 창 안 |
| 묶음·경보 | 조건 = "창 안에 A의 고리가 1개 이상". 1분 전 창에 고리가 없을 때만 경보. 그 경보의 `paths`는 E 시점 창 안의 **모든** A 고리. 고리가 남아 있는 동안 새로 닫힌 고리는 경보를 늘리지 않아요 |
| `params` | `{"window_hours": 96, "max_hops": 4}` |
| 금액 조건 | 없음 — 경로에서 통화가 바뀌면 비교 기준이 없어요 |
| `rule_facts` | `{paths, hops_by_path}` — 2.1 |
| 근거 거래 | 모든 고리의 거래(합집합) |

- **4홉을 고른 이유** — 9/1~9/10에서 3홉과 6개 룰 합집합 결과가 같았어요(정답 239/363). 4홉은 CYCLE 이벤트를 R04 자체로 더 잡아요(21/54). 10/28 "최대 3홉" 결정을 11/9 v2로 바꿨어요.
- **구현 방식** — 거래 단위로 바로 조인하면 2홉 체인만 하루 수천만 개라 터져요. **계좌 쌍(엣지)에서 먼저 고리 후보 계좌열을 찾고**(9/1~9/10 4홉 후보 524개), 그 후보만 거래 단위로 시간순 경로를 펼쳐요. 3홉과 4홉의 구현 차이는 후보 조인 한 단계예요.

**R04 구현 단계 (포트폴리오용 기록)** — 처음부터 최적화하지 않고 단계마다 측정해 남겨요.
1. **기준선** — 계좌 쌍 → 고리 후보 → 거래 단위 경로. 9/2 하루 실행 시간·경보 수·정답 대조를 기록.
2. **후보 줄이기** — 조인마다 시간 범위 조건을 먼저 걸고 `(from_account_key, ts)`·`(to_account_key, ts)` 인덱스를 타게.
3. **탐색 방식 비교** — 재귀 CTE vs 후보 거래만 메모리에 올려 Java로 탐색. 같은 결과인지 테스트로 고정.
4. **기록** — 단계마다 "실행 시간·읽은 행 수·경보 수"를 표로 남겨 "기준선 대비 몇 % 단축"으로 정리.

### R05_SCATTER_GATHER — 흩었다 모으기 〔확정 — v1 `R05_STACK` 교체〕

**왜 STACK을 바꿨나**: HI-Small의 STACK은 서로 관계없는 "A→M→B" 2단 중계 여러 개이고 중간에 통화가 바뀌는 경우가 많아요. 연속 경유 L단 룰과 모양이 맞지 않아요. STACK 모양은 이제 R03 환전 중계가 잡아요.

| 항목 | 내용 |
|---|---|
| 구조 | 출발 S → 서로 다른 중간 계좌 M₁…Mₖ → 도착 T. 각 Mᵢ는 S에게서 받은 **뒤에**(늦은 분) T로 보냄 |
| 대상 계좌 | T(모이는 계좌) |
| 창 · E | 1.1 · 1.2 — E = 경로를 완성하는 T **입금**의 분. 경로의 모든 거래가 창 안 |
| 조건 | 창 안에서 "S에게서 받은 뒤 T로 보낸" 서로 다른 중간 계좌 수 ≥ N인 출발 S가 있음. 거짓→참 |
| `params` | `{"window_hours": 96, "min_intermediates": 3}` |
| `rule_facts` | `{source_account_key, intermediates, paths}` — `paths`는 [S→Mᵢ, Mᵢ→T] 쌍들, 창 안 **모든 유효 경로**(2.1) |
| 근거 거래 | 모든 경로의 거래(합집합) |

### R06_GATHER_SCATTER — 모았다 흩기 〔확정 — v1 `R06_BIPARTITE` 교체〕

**왜 BIPARTITE를 바꿨나**: 10/28에 교체로 정했어요. HI-Small의 BIPARTITE는 두 집단 사이 거래가 계좌마다 1건씩이라 계좌 단위 룰로는 잡을 수 없어요.

| 항목 | 내용 |
|---|---|
| 대상 계좌 | 허브 계좌 H |
| 창 · E | 1.1 · 1.2 — E = H에 **입금이나 출금**이 있었던 분 |
| 조건 | 같은 창에서 서로 다른 송신 계좌 수가 `[min_distinct_senders, max_distinct_senders]` 안 **그리고** 서로 다른 수신 계좌 수가 `[min_distinct_receivers, max_distinct_receivers]` 안(양 끝 포함). 거짓→참. **입금·출금 선후는 따지지 않아요** — 정답 이벤트도 모으기·흩기가 며칠에 걸쳐 섞여 있어요 |
| 상한 | 입금 상대·출금 상대 **각각**에 걸어요(합계 아님). 상대가 수백·수천인 대형 계좌(근거가 특정 계좌에 몰려 lift를 깎는 경우)를 빼려는 거예요 |
| `params` | `{"window_hours": 96, "min_distinct_senders": 5, "max_distinct_senders": 100, "min_distinct_receivers": 5, "max_distinct_receivers": 100}` |
| `rule_facts` | `{distinct_senders, distinct_receivers, inbound_by_currency:[{currency, total_amount, transaction_count, transaction_ids}], outbound_by_currency:[…]}` |
| 근거 거래 | 창 안의 입금·출금 전부 |

### 2.1 `paths` (R03·R04·R05) — 확정 (10/28, ML 규약 §2.4)

- `int[][]`, R04·R05에서 **필수**(빈 배열·null 금지). 배열 하나가 경로 하나, 안은 **자금 이동 순서(시간순)** 실제 `transaction_id`. R03도 같은 모양을 써요(〔제안〕, 위 R03).
- 창 안의 **모든 유효 경로**를 담아요. 9/1~9/10 기준 경보당 최대 경로는 R04 16개, R05 106개예요. 경로를 하나만 담을 때와 경보(계좌·시점)는 같고 근거 거래만 조금 늘어요(R04 5,184 → 5,493, R05 606 → 657).
- 경로들의 거래 ID 합집합 = `transaction_ids`. 여러 경로가 같은 거래를 쓰면 경로마다 그대로 두고, 최상위 `transaction_ids`·건수는 **한 번만** 세요.
- 경로끼리는 첫 거래 시각순. 경로를 재정렬·삭제하지 않아요.
- 홉 = 경로의 거래 개수. 대상 계좌가 직접 끼지 않은 경로 거래(B→C)도 근거에 남아요 — 다만 대상 계좌의 입금·출금 합계에는 안 넣어요(ML 규약 §1.4).
- **룰 스캔이 저장 전에 검사**: 경로가 이어지는지, 시각이 늦어지는지, 모든 거래가 창 안인지, 합집합 = `transaction_ids`.
  - R04: A에서 시작해 A로 돌아오는지, `max_hops` 이하인지.
  - R05: 각 경로가 정확히 2건이고 첫 거래 송신 = S·둘째 거래 수신 = T·첫 거래 수신 = 둘째 거래 송신 = Mᵢ·둘째가 늦은 분·Mᵢ끼리 서로 다른지.
  - 어긋나면 경보를 만들지 않아요.
- STR III부: 대상 계좌가 직접 낀 거래만 III부에, 경로 전체는 별도 "자금 흐름 경로" 블록에(규약 v0.4 10번 (다)안). 블록에 넘길 모양은 채영님과 협의.
