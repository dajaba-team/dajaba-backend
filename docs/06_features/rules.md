## 1. 여덟 룰 공통 규칙

1. **룰 ID** — 위 표의 `rule_id` 문자열을 코드·`rules.rule_id`·학습 데이터에 그대로 써요.
2. **경보 1건** — (룰, 대상 계좌, 창) 한 조합. 대상 계좌는 룰마다 적어요.
3. **자기 계좌 거래 제외** — `is_self_transfer = true`는 모든 룰에서 세지도, 근거에 넣지도 않아요. 그래서 경보·경로·III부에 들어가지 않아요(0건).
4. **금액은 방향대로** — 입금은 `amount_received`·`currency_received`, 출금은 `amount_paid`·`currency_paid`(B7 ③, 11/2). 환산 없음, **다른 통화끼리 더하지 않아요.**
5. **통화 표기** — `rule_facts`의 통화는 원문 그대로(`US Dollar`). 코드(`USD`) 변환은 STR facts에서 AI가 해요.
6. **여러 통화** — 같은 계좌·룰·창이면 통화와 상관없이 **경보 1건**. 금액은 통화별 배열(`amounts_by_currency` 등). 단일 통화도 배열 한 항목(ML 규약 §2.3).
7. **근거 거래** — `transaction_ids` = 조건을 성립시킨 거래 전부(거래 id 순, 중복 없음). 통화별·방향별 `transaction_ids`의 합집합과 같아요. 상한 없음.
8. **시각** — 원천 시각은 **분 단위**(초 없음). 저장값은 시간대 없는 원본 시각. ML 피처는 `ts < reference_ts`.
9. **같은 분은 앞뒤를 모른다** — 분 단위라 같은 분 거래의 선후는 알 수 없어요. "A 다음에 B"가 조건인 룰(R03·R04·R05)은 **B가 A보다 늦은 분**일 때만 인정해요.
10. **`batch_date`** — 스캔한 날짜 = 평가 시점 E의 날짜(창 끝이 다음 날 00:00이어도).
11. **기준값이 없으면 실패** — `rules.params`에 필요한 키가 없거나 잘못되면 409 `INVALID_RULE_PARAMS`, 배치 FAILED. 코드에 기본값을 두지 않아요.

### 1.1 슬라이딩 창 (B7 — R01·R02·R03·R06·R07)

- 평가 시점 **E** = 대상 계좌에 그 룰이 보는 거래가 있었던 각 **분**. 같은 분의 거래는 함께 평가해요.
- 창 = **`[E+1분 − 창 길이, E+1분)`** — 뜻은 **`(E − 창 길이, E]`**: 지금 분 E는 넣고, 정확히 창 길이 전 그 분은 빼요(그래야 창이 딱 24시간). 저장값은 규약의 `[시작, 끝)` 표기라 1분 민 값이에요: `window_start = E+1분−24h`, `window_end = reference_ts = E+1분`.
- **거짓→참일 때만 경보.** 1분 전 창 `[E−24h, E)`의 조건과 비교해요. 참이 이어지는 동안은 경보를 더 만들지 않아요.
- 거래가 없는 동안 옛 거래가 창 밖으로 빠져 거짓이 되고, 다음 거래 분에 다시 참이 되면 **새 경보**.
- 날짜 경계: 전날 밤부터 참이 이어지면 다음 날에는 경보가 없어요. 전날을 스캔하지 않았어도 결과는 같아요.

예 (R02, N = 2): A로 11-07 06:00 S1, 07:00 S2, 08:00 S3 입금 → 06:00은 1명이라 없음, **07:00에 2명(1분 전 창은 1명) → 경보**, 08:00은 참 유지라 없음. 경보 창 `[11-06 07:01, 11-07 07:01)`, 근거 S1·S2 거래.

### R03_PASS_THROUGH — 입금 후 빠른 유출 〔v1〕

입금 1건마다 보지 않고 **24시간 누적**으로 봐요. 작은 입금 여러 건을 모아 한 번에 내보내는 경우를 잡고, 같은 계좌에 경보가 입금 수만큼 쌓이지 않게 하려는 거예요.

| 항목 | 내용 |
|---|---|
| 대상 계좌 | 입금받고 내보낸 계좌 |
| 평가 시점 | E = 그 계좌가 **출금**한 분 (출금이 생겨야 조건이 참이 될 수 있어서) |
| 창 | 1.1 슬라이딩 24h `[E+1분−24h, E+1분)` |
| 통화별 계산 | `in(c)` = 창 안 통화 c 입금 합(**E보다 앞선 분**만), `out(c)` = 창 안 통화 c 출금 합(**그 통화 첫 입금보다 늦은 분**만). 같은 분 출금은 입금 뒤 유출로 보지 않아요(1절 9) |
| 조건 | 어떤 통화 c든 `in(c) ≥ min_inbound_amount(c)` 이고 `out(c) ≥ P × in(c)`. 1분 전 창은 거짓 → 경보. 기준이 없는 통화는 평가하지 않아요 |
| `params` | `{"min_out_ratio": 0.8, "criteria_by_currency": [{"currency": "US Dollar", "min_inbound_amount": 10000}]}` |
| `rule_facts` | `{amounts_by_currency:[{currency, denominator(=in), out_sum, ratio, transaction_ids, criteria{min_inbound_amount, min_out_ratio}}]}` — ratio = out_sum / denominator, 1을 넘어도 그대로(ML 규약 §2.3). 조건을 채운 통화만 |
| 근거 거래 | 조건을 채운 통화의 창 안 입금(E 앞) + 첫 입금 뒤 출금 |
| 왜 누적 | 입금 1건 기준은 ① 쪼개 받은 돈을 한 번에 내보내면 못 잡고 ② 입금마다 경보가 생겨 "합칠지"를 따로 정해야 했어요. 누적 + 거짓→참이면 둘 다 해결되고 R01·R02와 같은 창 코드를 써요 |
| 한계 | 창 안에서 출금이 입금 사이사이에 섞이면 "그 입금의 돈"인지는 몰라요(잔액 추적 없음). 같은 통화만 보니 통화를 바꿔 내보내는 경유(STACK 일부)는 못 잡아요 |
| 정할 것 | 통화별 `min_inbound_amount`를 US Dollar 말고 더 넣을지(분포 보고) |

### R04_CYCLE — 순환 거래 〔v1〕

| 항목 | 내용 |
|---|---|
| 고리 | 거래 t1(A→B) … tk(→A), **2 ≤ k ≤ 3**. 앞 거래의 수신 계좌 = 다음 거래의 송신 계좌, 시각은 **분 단위로 엄격히 증가**(같은 분 불인정), 중간 계좌는 서로 다르고 A가 아님 |
| 대상 계좌 | A = 고리의 첫 거래(가장 이른 거래)의 송신 계좌. 그래서 같은 고리가 B·C 쪽에서 또 잡히지 않아요 |
| 평가 시점 | E = A로 **돌아오는 거래**(고리의 마지막 거래)의 분 |
| 창 | `[E+1분−72h, E+1분)` — 고리의 첫 거래가 이 안에 있어야 해요. `window_start = E+1분−72h`, `window_end = reference_ts = E+1분` |
| 묶음·경보 | 조건 = "창 안에 A의 고리가 1개 이상". 1분 전 창 `[E−72h, E)`에 고리가 없을 때만 경보(B7과 같은 거짓→참). 그 경보의 `paths`는 E 시점 창 안의 **모든** A 고리. 고리가 남아 있는 동안 새로 닫힌 고리는 경보를 늘리지 않아요 |
| `params` | `{"max_hops": 3, "window_hours": 72}` |
| 금액 조건 | 없음 — 경로에서 통화가 바뀌면 비교 기준이 없어요 |
| `rule_facts` | `{paths, hops_by_path}` — 2.1 |
| 근거 거래 | 모든 고리의 거래(합집합) |

**R04 구현 단계 (포트폴리오용 기록)** — 처음부터 최적화하지 않고 단계마다 측정해 남겨요.
1. **기준선** — SQL 자기 조인으로 2홉·3홉 고리(시간 증가·창 조건)를 그대로 찾기. 9/2 하루 실행 시간·경보 수·정답 대조를 기록.
2. **후보 줄이기** — 창 안에 입금과 출금이 둘 다 있는 계좌만 시작점으로, 조인마다 시간 범위 조건을 먼저 걸고 `(from_account_key, ts)`·`(to_account_key, ts)` 인덱스를 타게.
3. **탐색 방식 비교** — 재귀 CTE vs 후보 거래만 메모리에 올려 Java로 탐색. 같은 결과인지 테스트로 고정.
4. **기록** — 단계마다 "실행 시간·읽은 행 수·경보 수"를 표로 남겨 "기준선 대비 몇 % 단축"으로 정리.

### R05_SCATTER_GATHER — 흩었다 모으기 〔검토 — STACK 교체〕

**왜 STACK을 바꾸나**: HI-Small의 STACK은 서로 관계없는 "A→M→B" 2단 중계 여러 개이고 중간에 통화가 바뀌는 경우가 많아요. 연속 경유 L단 룰과 모양이 맞지 않고, 2단 중계 하나하나는 평범한 이체와 구별이 안 돼 오탐이 많아요.

| 항목 | 내용 |
|---|---|
| 구조 | 출발 S → 서로 다른 중간 계좌 M₁…Mₖ → 도착 T. 각 Mᵢ는 S에게서 받은 **뒤에**(늦은 분) T로 보냄 |
| 대상 계좌 | T(모이는 계좌) |
| 평가 시점 | E = T에 입금이 있었던 분 |
| 창 | `[E+1분−72h, E+1분)` |
| 조건 | 창 안에서 "S에게서 받은 뒤 T로 보낸" 서로 다른 중간 계좌 수 ≥ N인 출발 S가 있음. 거짓→참 |
| `params` | `{"min_intermediates": 5, "window_hours": 72}` |
| `rule_facts` | `{source_account_key, intermediates, paths}` — `paths`는 [S→Mᵢ, Mᵢ→T] 쌍들(2.1 규칙 그대로) |
| 확정 조건 | R04 기준선(2홉 조인)을 그대로 쓸 수 있으면 v1. 구현이 R04보다 확 무거우면 다른 룰로 교체 |

### R06_GATHER_SCATTER — 모았다 흩기 〔v1 — 3/3은 시작값, BIPARTITE 교체〕

**왜 BIPARTITE를 바꾸나**: 10/28에 교체로 정했어요. HI-Small의 BIPARTITE는 두 집단 사이 거래가 계좌마다 1건씩이라 계좌 단위 룰로는 잡을 수 없어요.

| 항목 | 내용 |
|---|---|
| 대상 계좌 | 허브 계좌 H |
| 평가 시점 | E = H에 입금이나 출금이 있었던 분 |
| 창 | 1.1 슬라이딩 24h |
| 조건 | 같은 창에서 서로 다른 송신 계좌 ≥ N_in **그리고** 서로 다른 수신 계좌 ≥ N_out. 거짓→참. **입금·출금 선후는 따지지 않아요** — 정답 이벤트도 모으기·흩기가 며칠에 걸쳐 섞여 있고, 선후 조건을 넣으면 24h 창에서 더 못 잡아요 |
| `params` | `{"min_distinct_senders": 3, "min_distinct_receivers": 3}` |
| `rule_facts` | `{distinct_senders, distinct_receivers, inbound_by_currency:[{currency, total_amount, transaction_count, transaction_ids}], outbound_by_currency:[…]}` |
| 근거 거래 | 창 안의 입금·출금 전부 |

#### 2.1 `paths` (R04·R05) — 확정 (10/28, ML 규약 §2.4)

- `int[][]`, R04·R05에서 **필수**(빈 배열·null 금지). 배열 하나가 경로 하나, 안은 **자금 이동 순서(시간순)** 실제 `transaction_id`.
- 경로들의 거래 ID 합집합 = `transaction_ids`. 여러 경로가 같은 거래를 쓰면 경로마다 그대로 두고, 최상위 `transaction_ids`·건수는 **한 번만** 세요.
- 경로끼리는 첫 거래 시각순. 경로를 재정렬·삭제하지 않아요.
- 홉 = 경로의 거래 개수. 대상 계좌가 직접 끼지 않은 경로 거래(B→C)도 근거에 남아요 — 다만 대상 계좌의 입금·출금 합계에는 안 넣어요(ML 규약 §1.4).
- **룰 스캔이 저장 전에 검사**: 경로가 이어지는지, 시각이 늦어지는지, 합집합 = `transaction_ids`, R04는 A에서 시작해 A로 돌아오는지·3홉 이하, R05는 각 경로가 정확히 2건이고 첫 거래 송신 = S·둘째 거래 수신 = T·첫 거래 수신 = 둘째 거래 송신 = Mᵢ·둘째가 늦은 분·Mᵢ끼리 서로 다른지. 어긋나면 경보를 만들지 않아요.
- STR III부: 대상 계좌가 직접 낀 거래만 III부에, 경로 전체는 별도 "자금 흐름 경로" 블록에(규약 v0.4 10번 (다)안). 블록에 넘길 모양은 채영님과 협의(11/13까지).

## 3. 버전·활성화

- 기준값을 바꾸면 기존 행을 고치지 않고 **새 버전 행**을 넣어요(`(rule_id, version)` unique). 같은 룰의 켜진 버전은 하나(`rules_active_uq`). 과거 경보는 옛 버전을 가리켜요(V005).
- 앱은 `rules`의 `is_active`·`updated_*`만 바꿀 수 있어요. 새 룰·새 버전은 Flyway 시드(지금) 또는 룰 기준값 API(SD 명세 API 6, 나중).
- 이미 성공한 날짜는 다시 스캔하지 않아요. 새 버전은 다음 스캔부터 적용돼요.
- 켜진 룰에 구현이 없으면 스캔이 실패해요(500, 배치 FAILED). 룰은 구현 PR에서 시드와 같이 켜요.
